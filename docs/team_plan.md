# Учебный NLP-проект: Telegram-бот для анализа русскоязычных отзывов

План для команды из 3–4 студентов на четыре недели. Редакция от 14 сентября 2026 года.
Это план работ: модели, метрики и возможности бота ниже описывают ожидаемый результат,
а не уже готовую реализацию.

## 1. Цель и границы проекта

Научиться готовить данные для классификации текста, обучать и сравнивать модели,
анализировать ошибки и подключать модель к небольшому приложению.

Результат — Telegram-бот, который принимает русскоязычный товарный отзыв текстом
или голосом и определяет общую тональность: отрицательную, нейтральную или
положительную. Для сообщений, не являющихся отзывами, предусмотрен класс `noise`.
Бот оценивает содержание сообщения; интонацию голоса он не анализирует.

Обязательная часть:

- один основной корпус отзывов и небольшая проверенная подборка `noise`;
- воспроизводимая подготовка данных и разбиение на train, validation и test;
- TF-IDF + Logistic Regression и один дообученный RuBERT;
- сравнение на одинаковых данных и разбор типичных ошибок;
- Telegram-бот с текстовым вводом и готовым Whisper для голосовых сообщений;
- небольшой тест на человеческих аудиозаписях, README и материалы для защиты.

Изображения, собственное обучение распознавания речи, генерация большого корпуса,
несколько трансформеров, веб-интерфейс и серверное развёртывание в обязательную часть
не входят. Полезный результат проекта не требует превосходства RuBERT над baseline:
корректно измеренное отсутствие улучшения тоже нужно объяснить.

## 2. Исследовательские вопросы

| Вопрос | Как проверяем |
|---|---|
| Даёт ли дообученный RuBERT преимущество перед TF-IDF? | Обучаем обе модели на одном train, выбираем настройки по validation, сравниваем на одном test |
| Какие сообщения вызывают ошибки, особенно на границе `neutral/noise`? | Поклассовые метрики, матрица ошибок и отдельная небольшая проверка по человеческой разметке |
| Насколько распознавание речи меняет качество? | Сравниваем предсказания на эталонных текстах и транскрипциях Whisper для одних и тех же записей |

Дополнительный вопрос, если хватает времени: как меняется качество на отзывах
из другого источника? Для него нужен внешний тест, который не участвует в обучении.
Падение качества на нём может быть связано и с доменом, и с разметкой; это следует
различать при интерпретации.

## 3. Что означают классы

| ID | Класс | Правило для разметки по содержанию текста | Пример |
|---:|---|---|---|
| 0 | `negative` | Преобладает отрицательная оценка товара или опыта покупки | «Швы разошлись после первой стирки» |
| 1 | `neutral` | Есть описание опыта без явной оценки либо положительные и отрицательные стороны без преобладающего вывода | «Пользуюсь неделю, пока сказать больше нечего» |
| 2 | `positive` | Преобладает положительная оценка товара или опыта покупки | «Удобные наушники, покупкой доволен» |
| 3 | `noise` | Нет отзыва об опыте покупки или использования: вопрос, приветствие, посторонняя реплика | «Когда появятся эти наушники?» |

Короткий текст может быть отзывом: «Отличные наушники» — `positive`.
Эмоциональность сама по себе не делает сообщение отзывом: «Ура, завтра выходной!» —
`noise`. Команды Telegram обрабатываются как команды и не передаются модели.

Смешанный отзыв не всегда нейтрален: «Звук хороший, но сломались за день, не советую» —
`negative`, поскольку есть явный отрицательный вывод. Фразы без достаточного контекста,
например «Цвет синий, размер 42», могут быть неоднозначными. При ручной разметке
отмечаем такие случаи и обсуждаем их; если договориться нельзя, не включаем их
в метрики ручного набора, указываем число исключений и показываем отдельно
как ограничение задачи. Основной test с исходными метками после разбиения не чистим
по субъективной сложности примеров.

**Рейтинг — приближение к тональности текста.** Для источников с оценками 1–5
используем отображение 1–2 → `negative`, 3 → `neutral`, 4–5 → `positive`.
Для готовых категориальных меток записываем отдельную таблицу преобразования.
Три звезды не гарантируют нейтральный текст, поэтому оценку по исходным меткам
дополняем небольшой независимой проверкой по содержанию.

Правила с 10–15 пограничными примерами фиксируем в начале первой недели.
Они одинаковы для обучения, ручного теста и голосовых сообщений.

## 4. Данные

### Основной корпус

Начинаем с [RuReviews](https://github.com/sismetanin/rureviews).
До обучения проверяем доступность, лицензию, исходные метки, пропуски и дубликаты.
В `data/README.md` записываем ссылку, имя файла, контрольную сумму, размер,
распределение классов и способ преобразования меток.

Для первичного аудита читаем около 100 примеров с представленными классами.
Это рабочая выборка для понимания данных, а не независимый финальный тест.
Если вычисления ограничены, используем фиксированную подвыборку обучающей части:
её размер и идентификаторы сохраняем, обе модели получают одни и те же примеры.

### Сообщения «не отзыв»

Собираем несколько сотен сообщений из разрешённых открытых источников и примеров,
написанных участниками. Начальный ориентир — 400–800, а не требование к достижению
определённой метрики. Сохраняем источник или автора и способ создания каждого примера.
Каждое сообщение проверяем вручную по общим правилам.

Включаем вопросы о товарах, обычные разговорные фразы, эмоциональные сообщения
без отзыва и бессвязный ввод. Важны близкие темы и разная длина: модель не должна
различать классы только по стилю магазина и разговорного корпуса. Нейтральные описания
личного опыта не записываем автоматически в `noise`.

Большую генерацию через LLM и шаблонное размножение фраз не используем.
Варианты одной исходной фразы считаем одной группой при разбиении.
В отчёте отдельно указываем долю примеров, написанных командой: их качество
не доказывает качество на реальных сообщениях пользователей.

### Независимая ручная проверка

Готовим отдельный набор из 80–120 сообщений, ориентир — по 20–30 на класс.
Отзывы берём из заранее зарезервированных реальных текстов, `noise` —
из отдельной подборки. Этот набор не пересекается с train, validation и test,
в том числе по близким формулировкам и известным группам.

Два участника независимо размечают сообщения, не видя рейтинга и ответов моделей,
затем обсуждают расхождения. Сохраняем исходные решения и число спорных случаев.
Итоговый набор и его метки не используем для изменения правил, обучения, настройки
моделей или выбора порога. Примерно равное число классов нужно для диагностики;
оно не отражает частоты сообщений в работающем боте.

### Внешний тест — по возможности

Кандидат — [WB Review Dataset](https://huggingface.co/datasets/Hplss/wb-review-dataset).
Проверяем доступность, лицензию и схему. Если присутствуют `text`, `pros` и `cons`,
собираем вход из непустых полей в фиксированном порядке: текст, достоинства, недостатки.
Порядок, подписи полей и обработку пропусков документируем; очистку и дедупликацию
выполняем уже по собранному тексту.

Используем небольшую фиксированную выборку только для финальной оценки.
Её не объединяем с обучающим корпусом. Если доступны только три класса отзывов,
считаем macro-F1 по этим трём целевым классам, сохраняя все предсказания модели:
ошибочный ответ `noise` не исключается из оценки. Отдельно показываем его долю.
Такую метрику не сравниваем напрямую с четырёхклассовой macro-F1.

Если источник недоступен или его подготовка задерживает основной эксперимент,
внешний тест пропускаем и указываем это в ограничениях. Если недоступен основной
корпус, проверяем этот кандидат как замену; решение и новый источник фиксируем
до разбиения данных.

## 5. Подготовка и разбиение

1. Сохраняем исходные поля и приводим тексты и метки к единой схеме.
2. Удаляем пустые тексты и точные дубликаты после нормализации пробелов и регистра
   для сравнения. Для входа модели сохраняем исходный регистр и пунктуацию.
3. Проверяем близкие дубликаты простым методом, например по символьным n-граммам,
   и вручную смотрим выборку найденных пар. Метод и порог сохраняем.
4. Резервируем независимую ручную проверку. Остальные данные делим примерно
   на 70% train, 15% validation и 15% test с `seed=42`.
5. Группы одинаковых и обнаруженных близких текстов, а также записи одного товара
   при наличии `product_id`, держим в одной части. Идентификатор товара связываем
   с источником, чтобы номера из разных корпусов не совпадали случайно.
6. Стремимся сохранить доли классов; отсутствие пересечений групп важнее точных
   процентов. Сохраняем полученные размеры, распределения и список записей каждой части.

Внешний и аудиотест также проверяем на совпадения с train и validation.
Примеры из первичного аудита, на которых уточняли правила, не включаем в финальные
тестовые наборы. Если поле товара отсутствует, явно пишем, что независимость
по товарам проверить нельзя.

TF-IDF и любую обучаемую предобработку настраиваем только на train.
Отдельная сложная инфраструктура версионирования не требуется: достаточно файлов
составов выборок, контрольной суммы исходных данных и сохранённой конфигурации.

## 6. Модели и оценка

Обе модели обучаем сразу на четыре класса:

- **Baseline:** word-level TF-IDF + Logistic Regression.
- **Трансформер:** `cointegrated/rubert-tiny2` с дообучением классификатора
  и энкодера. Это основной выбор для небольшого учебного проекта.

Не начинаем со сравнения нескольких RuBERT и отдельных трёхклассовых моделей.
Для baseline допускаем 2–3 настройки регуляризации; для RuBERT — короткий пробный
запуск и не более 2–3 конфигураций, если позволяет время. Число эпох ограничиваем,
лучший checkpoint выбираем по validation macro-F1. При дисбалансе проверяем
веса классов или уменьшение обучающей выборки преобладающих классов, не изменяя тест.

До конца первой недели пробуем обучение на небольшой выборке и проверяем
загрузку RuBERT и Whisper на машине для демонстрации. Фиксируем выбранную среду,
время пробного запуска и запасной способ доступа к вычислениям.
При нехватке ресурсов сначала уменьшаем batch size, длину входа и размер train.

Основные результаты:

- macro-F1 по четырём классам;
- precision, recall и F1 каждого класса, матрица ошибок;
- доля настоящих отзывов, принятых за `noise`, и доля `noise`, принятая за отзыв;
- результаты на независимом ручном наборе отдельно от основного test.

Качество обеих моделей сравниваем **на всех примерах без отказов**.
До финальной оценки фиксируем модели и настройки по validation, включая выбор
модели для бота. Затем оцениваем их на test и ручном наборе. Не выбираем победителя
для бота по тестовым результатам и не подстраиваем модель под найденные там ошибки.

Разбираем 30–50 ошибок выбранной модели, а если их меньше — все.
Группируем причины: спорная исходная метка, смешанная тональность, короткий текст,
сарказм, путаница `neutral/noise`. Для разработки используем ошибки validation;
финальные ошибки описываем в отчёте. Для каждого набора показываем размер.
Результаты небольших ручного и аудиотестов считаем диагностикой, а не точной
оценкой качества на всех русскоязычных отзывах.

## 7. Бот и минимальная архитектура

Одно Python-приложение на `aiogram 3.x`, локальный запуск через long polling.
Обучение выполняется отдельными командами; бот загружает готовую модель один раз.
Отдельные сетевые сервисы, база данных и постоянный хостинг для защиты не нужны.

```text
Telegram: текст ────────────────────┐
                                   ├→ классификатор → правило ответа → сообщение
Telegram: голос → Whisper → текст ──┘
```

Классификатор скрывает свою предобработку и имеет общий интерфейс:

```text
predict(text: str) -> {
    "label": str,
    "confidence": float,
    "probabilities": dict[str, float]
}
```

Для одной модели текстовый и голосовой сценарии используют одинаковую обработку
текста. Комплект модели содержит веса и токенизатор либо TF-IDF, порядок классов,
правила подготовки входа, максимальную длину, порог ответа и версию данных.

### Ответ пользователю

Используем одно общее правило в боте и оценочном скрипте:

1. Если уверенность ниже сохранённого порога — «Не уверен, попробуйте уточнить отзыв».
2. Иначе для `noise` — «Сообщение не похоже на отзыв о товаре».
3. Иначе показываем принятую тональность.

Начальный порог — 0.50. Уверенность — максимальная оценка класса
(`predict_proba` для baseline, softmax для RuBERT), а не гарантированная вероятность
правильного ответа. Отказ не является пятым обучаемым классом.

Для выбранной по validation модели проверяем пороги 0, 0.4, 0.5, 0.6, 0.7.
Выбираем порог с наименьшей долей ошибок среди принятых ответов при покрытии
не менее 80%; при равенстве выбираем большее покрытие, затем меньший порог.
Покрытие — доля примеров без отказа. Порог 0 означает отсутствие отказов.
Сохраняем порог в комплекте модели; в отчёте отдельно показываем покрытие и долю
ошибок среди принятых ответов. Эти показатели не заменяют основные метрики.

### Голос и обработка ошибок

Используем готовый `faster-whisper` с небольшой моделью, выбранной по пробному
запуску. Бот показывает транскрипцию вместе с результатом.
Пустая транскрипция означает «Не удалось распознать речь», а не `noise`.

Начальные ограничения для демонстрации: текст до 2000 символов, голос до 30 секунд
и 5 МБ, одно тяжёлое вычисление одновременно. Длинный ввод просим сократить.
Превышение лимита токенов модели обрабатываем одинаково при оценке и в боте;
правило усечения сохраняем, пользователю сообщаем, если учтена только часть текста.

Тяжёлые вызовы выполняем в одном выделенном исполнителе вне цикла событий бота.
Если он занят, просим повторить запрос позже: отдельная очередь в MVP не нужна.
В исполнителе выполняется и полный обход сегментов Whisper.
После 60 секунд ожидания сообщаем о задержке; уже начатое вычисление может продолжаться,
поэтому исполнитель остаётся занят до его завершения, поздний результат не отправляем.

Обрабатываем неподдерживаемый ввод, ошибки распознавания и отсутствие файлов модели.
При отсутствии токена или невозможности загрузить модель запуск завершается
с понятным сообщением. Токен хранится в переменной окружения, временные аудиофайлы
удаляются после обработки.

## 8. Проверка голосового сценария

Готовим 24–40 коротких записей от минимум трёх участников, с представленными
четырьмя классами, ориентир — по 6–10 записей на класс. Для каждой сохраняем
эталонный текст и согласованную метку.
Записи и их тексты не используем для обучения и настройки; это отдельный тест.
Часть записей делаем с умеренным бытовым шумом. Синтез речи не заменяет этот набор.

Одной зафиксированной моделью сравниваем:

- macro-F1 на эталонных текстах;
- macro-F1 на транскрипциях Whisper;
- разницу между этими значениями и несколько примеров ошибок распознавания;
- WER по всему набору, с описанным приведением регистра, пунктуации и чисел.

Пустую транскрипцию или технический сбой не исключаем молча:
показываем число таких случаев, а в итоговой macro-F1 голосового сценария
считаем их неправильными ответами для истинного класса. WER пустой транскрипции
рассчитываем как пропуск всех слов эталона. Все четыре целевых класса остаются
в расчёте macro-F1.

## 9. Работа по неделям

| Неделя | Работа | Проверяемый результат |
|---|---|---|
| 1. Данные и первый запуск | Уточнить классы, проверить источник, собрать `noise`, зарезервировать ручной тест, подготовить сплиты, обучить baseline, проверить вычисления | Сохранены данные и настройки разбиения, есть validation-метрики baseline и пробный запуск RuBERT; каркас бота отвечает с заглушкой |
| 2. Модели и текст | Дообучить RuBERT, сравнить по validation, разобрать ошибки, выбрать модель и порог, подключить её к боту | Бот классифицирует текст, модель загружается из сохранённого комплекта |
| 3. Голос и сборка | Подключить Whisper, закончить независимую ручную разметку, записать аудиотест, проверить ограничения и запуск другим участником | Текст и голос работают на машине для защиты; функции и настройки зафиксированы |
| 4. Оценка и защита | Провести финальные тесты, описать ошибки и ограничения, оформить README и отчёт, подготовить презентацию и репетицию | Таблица результатов, воспроизводимые команды и готовая демонстрация |

До фиксации конфигурации проверяем голос на отдельных отладочных записях.
Финальные ручной и аудиотесты открываем для оценки на четвёртой неделе.
Критические ошибки кода исправляем и документируем; если они затронули метрики,
повторяем соответствующую оценку и явно указываем причину.

Для трёх участников: первый отвечает за данные и baseline, второй — за RuBERT
и оценку, третий — за бота и Whisper. Для четырёх отдельный участник берёт оценку,
проверки и сборку отчёта. Разметку, аудиозаписи и подготовку защиты выполняем вместе.
В конце каждой недели проверяем совместный запуск, чтобы интеграция не оставалась
на последние дни.

## 10. Репозиторий и проверки

Начальная структура; новые файлы добавляем по мере необходимости:

```text
ru-review-sentiment-bot/
├── README.md                 # установка, команды, ограничения
├── requirements.txt          # проверенные версии зависимостей
├── .env.example              # имена переменных без секретов
├── configs/                  # данные и обучение
├── data/README.md            # источники, разметка, подготовка и версии
├── src/
│   ├── prepare_data.py
│   ├── train_baseline.py
│   ├── train_transformer.py
│   ├── evaluate.py
│   ├── classifier.py         # загрузка и общий интерфейс
│   ├── service.py            # ограничения и общее правило ответа
│   ├── speech.py
│   └── bot.py
├── tests/
├── reports/                  # метрики, графики и итоговый отчёт
└── docs/team_plan.md
```

EDA можно делать в ноутбуке, но подготовка данных, обучение и оценка должны
запускаться командами из README. Не создаём отдельный документ на каждый модуль:
правила данных храним в `data/README.md`, инструкции запуска — в README,
эксперименты и выводы — в одном отчёте.

Достаточный набор автоматических проверок:

- корректность преобразования меток и сборки полей отзыва;
- отсутствие пустых текстов, неизвестных меток и пересечений текстов/известных групп;
- обучение baseline на небольшой выборке, сохранение и загрузка с теми же ответами;
- совпадение порядка классов и решения об отказе в боте и оценочном скрипте;
- прохождение текста и транскрипции через общий путь, включая пустой результат и ошибку.

Перед защитой другой участник проверяет установку и запуск по README,
реальный текстовый и голосовой запрос, слишком длинный ввод и поведение занятого бота.
Заглушки подходят для проверки связей компонентов; ими нельзя подтвердить
работоспособность реальной модели и Whisper.

Исходные данные, аудио, веса моделей и секреты не коммитим. До появления этих файлов
дополняем `.gitignore` используемыми путями и форматами, включая `safetensors`
и сохранённый baseline. В README описываем получение или воспроизведение
комплекта модели. Конфигурации, код, составы выборок без текстов и итоговые
метрики сохраняем в Git.

## 11. Критерии завершения и приоритеты

Проект готов к защите, когда:

1. Понятны определения классов, источники и ограничения разметки.
2. Обе модели обучены и сравнены на одинаковом test без утечек и подбора по нему.
3. Есть небольшие независимые проверки человеческой разметки и голосового сценария.
4. Бот принимает текст и голос, показывает транскрипцию и обрабатывает основные ошибки.
5. Другой участник может повторить запуск; отчёт содержит результаты и объяснение ошибок.

При нехватке времени сначала отказываемся от внешнего теста и дополнительных
настроек моделей, затем уменьшаем train и используем минимальные объёмы ручного
и аудиотестов из этого плана. В боте можно использовать baseline, если он лучше
по validation или RuBERT не подходит демонстрационной машине; сравнение с RuBERT
при этом остаётся частью исследования.

Проблему с доступом к обучению RuBERT поднимаем в первую неделю. Если её не удалось
решить, согласуем сокращённый объём с преподавателем и явно отмечаем невыполненную
часть, а не объявляем исходный план завершённым.
Не сокращаем проверку утечек, честную оценку и подготовку воспроизводимого запуска.
Резерв для демонстрации — заранее проверенные примеры и запись работы бота.

## 12. Будущая работа

Изображения — отдельное возможное продолжение, без обещания закончить его
за дополнительную неделю. Сначала нужна гипотеза, например: помогает ли фотография
дефекта понять короткий отзыв, и разрешённые парные данные «отзыв + фото + метка».
Каталожная фотография сама по себе не подтверждает отношение покупателя.

Если продолжение состоится, сравниваем текст, изображение и их объединение:
головы моделей обучаем на одном парном train без пересечения товаров между выборками,
для текстового энкодера сохраняем
одинаковую инициализацию и режим заморозки, даём сопоставимый бюджет настройки.
Конфигурации выбираем по общему validation, итоговый test смотрим после их фиксации.
Нерелевантная фотография не меняет тональность настоящего отзыва на `noise`;
проверку соответствия изображения рассматриваем отдельно.
Первый результат может быть экспериментом без добавления фотографий в Telegram.
