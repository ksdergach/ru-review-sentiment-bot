# NLP Project: Telegram-бот для классификации тональности русскоязычных отзывов

## Цель проекта

Разработать Telegram-бота, который принимает:

- русскоязычный текстовый отзыв;
- голосовое сообщение на русском языке;
- на расширенном этапе — изображение вместе с текстом.

Полученный текст классифицируется по четырём классам:

| ID | Класс | Значение |
|---:|---|---|
| 0 | `negative` | Отрицательный отзыв |
| 1 | `neutral` | Нейтральный или смешанный отзыв |
| 2 | `positive` | Положительный отзыв |
| 3 | `noise` | Сообщение не является отзывом |

Основная учебная задача — supervised-классификация текста. Голосовые сообщения
распознаются готовой моделью Whisper, после чего полученный текст передаётся в тот же
классификатор. Собственная аудиомодель не обучается, аудиодатасет для обучения не
собирается и не ищется.

Документ содержит две версии проекта:

1. **MVP-план** — обязательная часть, рассчитанная на команду из 3–4 человек и четыре недели.
2. **Полный план** — MVP и дополнительная пятая неделя на мультимодальность.

Пятая неделя находится за пределами основного месячного срока и рассматривается как расширение, если преподаватель разрешит дополнительное время или обязательная часть будет завершена раньше.

# Версия 1. MVP на 4 недели

## 1. Результат MVP

К концу четвёртой недели должны быть готовы:

- проверенный датасет реальных русскоязычных отзывов;
- воспроизводимые `train`, `validation` и `test`;
- baseline `TF-IDF + Logistic Regression`;
- одна дообученная модель RuBERT;
- сравнение моделей по macro-F1 и поклассовым метрикам;
- единый классификатор `negative/neutral/positive/noise`;
- Telegram-бот с текстовым и голосовым вводом;
- Whisper в режиме инференса;
- небольшой тест на реальных голосовых записях;
- анализ ошибок, README и материалы для защиты.

## 2. Что не входит в MVP

Чтобы уложиться в один месяц, в обязательную часть не входят:

- обучение собственной модели распознавания речи;
- обучение классификатора по аудиопризнакам;
- TTS-аугментация обучающих данных;
- сравнение большого числа трансформеров;
- каскад из отдельных моделей `review/noise` и `sentiment`;
- сложная LLM-генерация большого корпуса;
- мультимодальная модель;
- мобильное или веб-приложение помимо Telegram-бота.

## 3. Данные MVP

### 3.1. Основной источник

**RuReviews** — реальные русскоязычные отзывы на женскую одежду и аксессуары. Исходные пользовательские оценки автоматически преобразованы в классы тональности.

Источник: <https://github.com/sismetanin/rureviews>.

Перед использованием необходимо зафиксировать:

- точный файл и его контрольную сумму;
- размер и распределение классов;
- лицензию;
- схему исходных меток;
- результаты ручной проверки 100 случайных отзывов;
- долю пустых текстов и дубликатов.

### 3.2. Дополнительный источник

**WB Review Dataset** рассматривается как источник дополнительных реальных отзывов или как внешний тест:

<https://huggingface.co/datasets/Hplss/wb-review-dataset>.

Он включается только после проверки лицензии, качества текстов и согласованности рейтинга с содержанием. Поле `product_id` используется для группового разбиения.

На первой неделе команда выбирает один из двух вариантов использования данных:

- RuReviews для обучения, WB Review Dataset для внешнего теста;
- объединение двух источников для обучения с отдельным отложенным тестом из одного домена.

Первый вариант предпочтительнее для понятного междоменного эксперимента.

Чтобы отказ одного источника не заблокировал проект, используется резервная цепочка:

1. **Основной кандидат для внешнего теста — WB Review Dataset.**
2. **Резерв №1 — Kaggle «Сентимент-анализ отзывов на товары».** Источник уже найден
   командой, но до начала работы в `data/README.md` необходимо записать точный URL,
   владельца, файлы `light/full`, лицензию и схему разметки. Пока точный URL не
   зафиксирован, источник не считается воспроизводимо подтверждённым.
3. **Резерв №2 — русскоязычные отзывы на мобильные телефоны с рейтингами 1–5:**
   <https://www.kaggle.com/datasets/theovall/phonereviews>. Это сырой датасет, поэтому
   он принимается только после проверки пропусков, аномалий, дубликатов, лицензии и
   соответствия рейтинга тексту.

Если основной кандидат не проходит аудит в первый день, команда сразу переходит к
резерву и не тратит неделю на восстановление одного источника.

### 3.3. Схема меток

Единое отображение:

- оценки 1–2 → `negative`;
- оценка 3 → `neutral`;
- оценки 4–5 → `positive`;
- нерелевантное сообщение → `noise`.

Для готовых категориальных меток преобразование задаётся отдельной таблицей. Метка `-1` не используется.

### 3.4. Класс `noise`

В класс включаются реальные нерелевантные сообщения:

- приветствия и команды;
- бытовые фразы;
- вопросы без оценки;
- нейтральные информационные сообщения;
- случайные и бессвязные реплики.

Часть таких сообщений можно взять из открытого разговорного корпуса или RuSentiment, но каждый кандидат должен соответствовать определению «не отзыв». Формирование класса только по названию исходного датасета запрещено.

Разрешается добавить небольшое число синтетических примеров, если:

- они отмечены `is_synthetic=true`;
- находятся только в `train`;
- не преобладают над реальными сообщениями;
- validation и test содержат только реальные или вручную подготовленные сообщения.

## 4. Подготовка и разбиение данных

Перед разбиением выполняются:

1. удаление пустых записей;
2. приведение меток к единому словарю;
3. удаление точных дубликатов;
4. поиск близких дубликатов;
5. сохранение `source`, исходной оценки и `product_id`, если он существует;
6. формирование статистического отчёта.

Основное разбиение:

- `train` — 70%;
- `validation` — 15%;
- `test` — 15%;
- фиксированный `seed=42`;
- стратификация по целевому классу;
- группировка по `product_id`, когда поле доступно;
- одинаковые и близкие тексты находятся только в одном сплите;
- синтетические примеры разрешены только в `train`.

Отдельный `external_test` не используется для подбора модели и гиперпараметров.

Автоматические проверки должны подтверждать:

- отсутствие пересечения текстов и групп между сплитами;
- отсутствие неизвестных меток;
- отсутствие синтетики в validation/test;
- сохранение приемлемого распределения классов.

## 5. Модели MVP

### 5.1. Baseline

- word- и/или character-level TF-IDF;
- Logistic Regression;
- `class_weight="balanced"`, если дисбаланс подтверждён статистикой.

Baseline обучается в двух вариантах:

- три класса тональности без `noise`;
- четыре класса с `noise`.

### 5.2. Основная модель

Используется одна базовая предобученная русскоязычная модель:

- `cointegrated/rubert-tiny2` при ограниченных ресурсах;
- либо `ai-forever/ruBert-base`, если доступно подходящее GPU.

Окончательный выбор делается в начале второй недели после короткого smoke-теста. Модели, уже дообученные на sentiment analysis, не используются как основная инициализация, если нельзя исключить пересечение их обучающих данных с нашим тестом.

Основная модель обучается на четыре класса. Трёхклассовый RuBERT допускается только как короткая контрольная точка, если это не задерживает интеграцию.

Доступ к вычислениям закрывается отдельным **GPU-gate до конца первой недели**. Команда
фиксирует:

- основную платформу: локальная машина, Google Colab, Kaggle Notebooks или
  университетский кластер;
- резервную платформу;
- ответственного за окружение и доступ;
- доступный объём GPU-времени и хранилища;
- результат пробного запуска обучения на небольшой выборке;
- оценку времени одной эпохи;
- fallback на `cointegrated/rubert-tiny2`, если `ruBert-base` не помещается в память или
  не укладывается в срок.

Если GPU-gate не пройден, команда не ждёт вторую неделю, а сразу переключается на
облегчённую модель.

## 6. Метрики MVP

Основная метрика — `macro-F1`.

Дополнительно считаются:

- precision, recall и F1 каждого класса;
- weighted-F1;
- accuracy как вторичная метрика;
- confusion matrix;
- доля отзывов, ошибочно отнесённых к `noise`;
- доля шума, ошибочно принятого за отзыв;
- результаты отдельно по источникам.

Лучшая модель выбирается только по validation. Test используется один раз после выбора конфигурации.

Для финальной модели вручную анализируется не менее 100 ошибок. Причины группируются: плохая исходная метка, смешанная тональность, сарказм, короткий текст, доменный сдвиг, ошибка `noise` и ошибка Whisper.

## 7. Telegram-бот MVP

Используется `aiogram 3.x`.

Текстовый пайплайн:

```text
сообщение → preprocessing → классификатор → класс и уверенность → ответ
```

Голосовой пайплайн:

```text
Telegram voice → OGG/OPUS → Whisper/faster-whisper → транскрипция
               → тот же preprocessing → тот же классификатор → ответ
```

Для `noise` бот сообщает, что сообщение не похоже на отзыв. При низкой уверенности бот не должен выдавать категоричный ответ.

Начальный порог отказа фиксируется в `configs/classifier.yaml`, чтобы модель и бот не
использовали разные правила:

```yaml
abstain_threshold: 0.50
threshold_selection: validation
minimum_coverage: 0.80
```

Правило MVP: если `max_softmax < abstain_threshold`, бот отвечает «Не уверен в
тональности сообщения». Значение `0.50` является только стартовым. Финальный порог
подбирается по validation-набору, сохраняется вместе с моделью и сопровождается
графиком или таблицей «coverage — доля ошибок». Test для выбора порога не используется.
Поскольку softmax-оценка не гарантирует калиброванную вероятность, в отчёте она
называется уверенностью модели, а не истинной вероятностью правильного ответа.

`coverage` определяется как доля validation-примеров, для которых модель не отказалась
от ответа. `minimum_coverage` является жёстким ограничением: итоговый
`abstain_threshold` выбирается как максимальный порог, при котором
`coverage >= minimum_coverage`. Если несколько проверяемых порогов дают одинаковое
coverage, выбирается вариант с лучшим macro-F1 среди принятых ответов. Таким образом,
значение `minimum_coverage: 0.80` требует, чтобы модель классифицировала не менее 80%
примеров validation-набора.

Нужно обработать:

- пустой ввод;
- слишком длинное сообщение;
- пустую транскрипцию;
- неподдерживаемый файл;
- таймаут Whisper;
- ошибку загрузки модели;
- отсутствие Telegram-токена.

Транскрипция голосового сообщения показывается пользователю рядом с результатом.

## 8. Аудиотест MVP

Аудиофайлы используются только для тестирования.

Команда готовит небольшой набор реальных записей:

- ориентир — 40–60 сообщений;
- не менее трёх дикторов;
- представлены все четыре класса;
- разный темп речи;
- часть записей содержит умеренный бытовой шум;
- для каждого файла есть ручная эталонная транскрипция.

Измеряются:

- WER Whisper;
- macro-F1 на эталонных текстах;
- macro-F1 после Whisper;
- падение качества из-за распознавания речи;
- примеры ошибок полного пайплайна.

Silero TTS можно использовать только для технического smoke-теста, но не вместо человеческих записей и не для обучения.

## 11. Критерии готовности MVP

MVP готов, если:

- модель обучена на реальных русскоязычных отзывах;
- данные, лицензии и схема меток документированы;
- сплиты воспроизводимы и не пересекаются;
- baseline и RuBERT сравнены по одинаковому тесту;
- показаны macro-F1, поклассовые метрики и confusion matrix;
- отдельно оценён класс `noise`;
- бот принимает текстовые и голосовые сообщения;
- голос проходит через готовый Whisper, а не через собственную ASR-модель;
- проведён тест на реальных аудиозаписях;
- установка и запуск описаны в README;
- типичные ошибки и ограничения перечислены в отчёте.

# Версия 2. Полный план на 5 недель

## 12. Состав полного проекта

Полный проект включает весь MVP без изменений. Недели 1–4 выполняются по описанному выше календарю. Мультимодальность добавляется только после фиксации работоспособной версии текстово-голосового бота.

Полная версия не заменяет и не откладывает обязательную часть. На начало пятой недели должны существовать:

- зафиксированный датасет MVP;
- финальная текстовая модель;
- Telegram-бот с текстом и Whisper;
- итоговые метрики MVP;
- отдельный Git-тег или сохранённая стабильная версия, к которой можно вернуться.

Если эти условия не выполнены, пятая неделя используется для завершения MVP, а мультимодальность переносится в раздел будущей работы.

### Фоновая подготовка мультимодальности в недели 1–4

Пятая неделя не должна начинаться с холодного поиска данных. Один участник ведёт
неблокирующую исследовательскую задачу с лимитом примерно 1–2 часа в неделю:

- **неделя 1:** сформулировать требования к парному датасету
  `изображение + текст отзыва + метка`;
- **неделя 2:** найти 2–3 возможных источника и записать прямые ссылки;
- **неделя 3:** проверить лицензии, схему данных и небольшие случайные выборки;
- **неделя 4:** выбрать основного кандидата и резерв либо зафиксировать, что подходящих
  данных нет.

Этот трек не включает обучение мультимодальной модели и не должен отнимать ресурсы у
MVP. К концу четвёртой недели результатом является короткая карточка кандидата, а не
обязательный готовый датасет. День 1 пятой недели используется для окончательного
data-gate уже исследованного источника.

## 13. Цель мультимодального расширения

Проверить исследовательскую гипотезу:

> Может ли представление изображения улучшить классификацию тональности отзыва по сравнению с моделью, использующей только текст?

Основной сценарий — пользователь отправляет фотографию товара вместе с текстом или подписью-отзывом.

```text
текст/подпись → текстовый энкодер ─────────┐
                                           ├→ обучаемый fusion-слой → 4 класса
изображение → CLIP/ruCLIP image encoder ───┘
```

Фото без текста не считается обычным отзывом. В продуктовой версии бот просит добавить подпись. Экспериментальный image-only режим допускается только как отдельная контрольная модель.

## 14. Данные для мультимодальности

Для обучения нужны парные данные:

```text
изображение + текст отзыва + метка тональности
```

Нельзя просто объединить CLIP- и BERT-эмбеддинги во время инференса, если fusion-слой не обучался на таких парах.

До начала реализации проводится отдельный data gate:

- найден законно используемый парный датасет либо подготовлена небольшая учебная выборка;
- подтверждена связь изображения с объектом отзыва;
- сохранены лицензия и источник изображения;
- отсутствуют одинаковые товары в разных сплитах;
- представлен каждый целевой класс;
- объём достаточен хотя бы для ограниченного сравнительного эксперимента.

Кандидаты для этого gate должны быть предварительно исследованы в фоновом треке недель
1–4. Если к концу четвёртой недели нет ни одного допустимого источника, команда не
тратит пятую неделю на бесконтрольный поиск, а оформляет мультимодальность как будущую
работу.

Если полноценного парного датасета нет, допустим упрощённый исследовательский прототип на небольшой вручную проверенной выборке. Его результаты нельзя представлять как надёжную продуктовую метрику.

Класс `noise` в мультимодальном эксперименте можно ограничить следующими случаями:

- нерелевантный текст с товарным изображением;
- отзыв с нерелевантным изображением;
- нерелевантные и текст, и изображение.

Эта часть выполняется только при достаточном количестве времени и данных.

## 15. Архитектура мультимодальной модели

Минимальный вариант:

1. текст кодируется уже выбранным RuBERT;
2. изображение кодируется замороженным CLIP/ruCLIP;
3. размерности приводятся небольшими линейными слоями;
4. представления конкатенируются;
5. fusion-слой и классификационная голова обучаются на парных данных.

Чтобы уложиться в неделю, сначала замораживаются оба энкодера и обучается только fusion-голова. Размораживание последних слоёв допускается лишь при стабильном baseline и достаточном GPU.

Обязательны три сравнимых режима:

| Эксперимент | Вход | Назначение |
|---|---|---|
| M0 | Только текст | Мультимодальный baseline |
| M1 | Только изображение | Проверка информативности изображения |
| M2 | Текст + изображение | Проверка гипотезы об улучшении |

Все три режима оцениваются на одном парном test-наборе. Главная метрика — macro-F1. Также сравниваются поклассовые F1 и случаи, где изображение исправило или испортило решение текстовой модели.

## 16. Telegram-сценарий с изображением

Бот поддерживает:

- фото с подписью — передать оба входа в мультимодальную модель;
- фото без подписи — попросить написать отзыв;
- текст без фото — использовать стабильную текстовую модель MVP;
- ошибку image encoder — сообщить об ошибке и, если есть подпись, предложить результат text-only модели.

Мультимодальная ошибка не должна нарушать текстовый и голосовой сценарии MVP.

## 17. Неделя 5 — мультимодальность

### День 1. Проверка данных и baseline

- завершить data gate;
- подготовить парные сплиты без пересечения товаров;
- оценить текстовую модель M0 на парном тесте;
- утвердить размер эксперимента и критерий остановки.

### День 2. Image encoder

- подключить CLIP/ruCLIP;
- реализовать получение и кэширование image embeddings;
- проверить формы тензоров и обработку повреждённых файлов;
- получить результат M1.

### День 3. Fusion

- реализовать fusion-голову;
- обучить M2 с замороженными энкодерами;
- подобрать минимальные параметры по validation;
- сохранить модель и конфигурацию.

### День 4. Оценка и бот

- сравнить M0, M1 и M2;
- провести абляцию;
- подключить обработчик фото;
- сохранить text-only fallback;
- добавить интеграционные тесты.

### День 5. Документация и демонстрация

- разобрать ошибки мультимодальной модели;
- документировать ограничения данных;
- добавить результаты в отчёт и презентацию;
- подготовить примеры, где изображение помогает и мешает;
- провести end-to-end демонстрацию текста, голоса и фото.

## 18. Критерии успеха полной версии

Полная версия считается завершённой, если:

- MVP остаётся полностью работоспособным;
- происхождение парных данных и лицензии задокументированы;
- M0, M1 и M2 сравниваются на одинаковом тесте;
- fusion-модель действительно обучена, а не просто объединяет эмбеддинги в инференсе;
- результат M2 измерен и честно сопоставлен с text-only M0;
- бот корректно обрабатывает фото с подписью и фото без подписи;
- предусмотрен text-only fallback;
- ограничения небольшой мультимодальной выборки явно указаны.

Улучшение M2 относительно M0 желательно, но отрицательный результат также допустим как исследовательский вывод, если эксперимент проведён корректно.

## 19. Приоритеты при нехватке времени

Работы сокращаются в следующем порядке:

1. отказаться от частичного размораживания энкодеров;
2. отказаться от сложной обработки мультимодального `noise`;
3. оставить только замороженный image encoder и простую fusion-голову;
4. оформить мультимодальность как offline-эксперимент без обработчика Telegram;
5. полностью перенести мультимодальность в будущую работу.

Нельзя ради мультимодальности сокращать проверку данных, честную оценку основной модели, голосовой тест или стабильность MVP.

## 22. Организационные правила

- Большие данные, аудио, Telegram-токены и чекпоинты не коммитятся.
- Версии данных и конфигураций фиксируются для каждого эксперимента.
- Test не используется для подбора гиперпараметров.
- Изменения интерфейса между моделью и ботом согласуются внутри команды.
- К концу каждой недели проводится общая интеграционная проверка.
- Каждый участник документирует команды запуска своей части.
- До конца третьей недели выбирается способ демонстрационного развёртывания. Вариант по
  умолчанию — локальный запуск через Telegram long polling: он не требует публичного
  адреса или webhook. VPS используется только при наличии готового доступа и времени
  на проверку.
- В `docs/deployment.md` фиксируются окружение, команда запуска, переменные окружения,
  порядок проверки бота и резервный сценарий демонстрации.
- Удалённый репозиторий, таск-трекер и сторонние интеграции создаются только после отдельного командного решения.
