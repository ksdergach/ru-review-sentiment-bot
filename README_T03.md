# T03 — подготовка русскоязычных split'ов и аудит утечек

Этот набор файлов реализует Issue **T03** без нового случайного разбиения исходного корпуса.

## Что делает `src/prepare_data.py`

Одна команда:

```bash
python src/prepare_data.py --config configs/data_prep.json
```

выполняет:

1. полную проверку конфигурации: отсутствующее или некорректное значение приводит к явной ошибке, а не к тихой подстановке дефолта;
2. проверку наличия и схемы исходных Parquet;
3. SHA-256 каждого исходного файла до и после работы;
4. проверку обязательных полей, пропусков, типов, пустых и состоящих только из пробелов текстов, допустимых языков;
5. отбор только `review_language == "ru"`;
6. фиксированное сопоставление классов `negative=0`, `neutral=1`, `positive=2`;
7. создание стабильного `record_id = <исходный файл>#row=<номер строки>`;
8. выявление конфликтов меток: одинаковый нормализованный текст с разными `review_sentiment`;
9. точную дедупликацию по нормализованному ключу;
10. приоритет удаления **test > validation > train**;
11. сохранение test без удаления строк, включая внутренние дубликаты;
12. воспроизводимый поиск похожих текстов по char-n-gram Jaccard;
13. применение near-duplicate удаления **только после ручного решения `duplicate`**;
14. проверку пересечений `movie_id` и нормализованных точных текстов;
15. проверку, что каталоги вывода не совпадают с каталогом исходных Parquet;
16. сохранение итоговых `train/validation/test` в Parquet;
17. аудит исключённых ID, конфликтов меток, итоговых распределений и контрольных сумм;
18. опциональную фиксированную стратифицированную подвыборку train с `seed=42`.

## Нормализация текста

Ключ дедупликации строится так:

```text
NFC  ->  casefold  ->  удаление невидимых символов (U+200B..U+200D, U+2060, U+FEFF)  ->  схлопывание пробелов
```

Unicode-нормализация обязательна: без неё визуально одинаковые тексты,
записанные разными последовательностями код-пойнтов (например «й» как U+0439
против U+0438 + U+0306), считаются разными и проходят мимо точной
дедупликации. На реальных данных проекта такой случай существует и даёт
утечку train↔validation.

`review_text` в подготовленных данных сохраняется буквально как в исходном
Parquet: регистр, пунктуация, пробелы и эмодзи не изменяются. Нормализованный
текст существует только во временных служебных колонках (`_exact_key`,
`_near_key`) и никогда не попадает в выходные файлы.

Исходные Parquet не перезаписываются.

## Конфликты меток

Одинаковый нормализованный текст с разными метками не скрывается обычной
дедупликацией. Такие группы:

- выявляются до дедупликации, по всем трём split'ам сразу;
- попадают в аудит отдельными счётчиками, в том числе с разбивкой
  «внутри одного split» и «между split'ами»;
- полностью перечисляются в `reports/data_prep/label_conflicts.csv`
  (только идентификаторы, метки и SHA-1 ключа — без текстов отзывов).

Само удаление остаётся за обычным приоритетом split'ов, и каждая удалённая
строка имеет причину в `excluded_ids.csv`. Отдельно считается, сколько строк
было удалено как подтверждённые near-duplicates при несовпадающей метке —
это повод пересмотреть решение вручную.

Файлы в `reports/data_prep/` не содержат текстов отзывов и годятся для Git.
Файл `artifacts/data_prep/near_duplicate_review.csv` содержит исходные тексты
пар и нужен только для ручного аудита — каталог `artifacts/data_prep/`
исключён в `.gitignore`.

`audit.json` содержит поле `status`. Значение `in_progress` означает, что
запуск не завершился: отчёты в этом случае несогласованы между собой и им
нельзя доверять.

## Ручная проверка near-duplicates

В `configs/data_prep.json` заранее зафиксирован алгоритм поиска кандидатов:

- char 3-grams;
- Jaccard threshold = `0.90`;
- minimum text length = `40`;
- minimum length ratio = `0.85`;
- prefix/suffix blocking для группировки сравнений;
- `max_block_pairs` — бюджет пар на один блок, при превышении явная ошибка.

Порог не подбирается по test-метрикам.

После первого запуска:

1. открыть `artifacts/data_prep/near_duplicate_review.csv`;
2. вручную просмотреть кандидатов — файл содержит не только тексты, но и
   `left_label` / `right_label`, флаг `labels_conflict`, `left_movie_id` /
   `right_movie_id` и флаг `same_movie_id`, без которых невозможно отличить
   копию от пары «похожий текст, разные метки»;
3. для нужных пар перенести `pair_id` в `configs/near_duplicate_decisions.csv`;
4. заполнить `decision` только одним из значений:
   - `duplicate` — подтверждённая копия;
   - `not_duplicate` — похожий, но самостоятельный текст;
5. повторно запустить подготовку.

Высокий similarity сам по себе **никогда не удаляет строку**.

### Полнота поиска кандидатов

Блоки никогда не отбрасываются. Внутри каждого блока сравниваются все пары,
с дешёвым предварительным фильтром по `length_ratio_min`. Ограничение
`max_block_pairs` — это бюджет на один блок: при его превышении подготовка
завершается явной ошибкой с предложением ужесточить параметры блокирования,
а не молча теряет часть сравнений.

Так было не всегда. В первой версии блоки крупнее `max_block_size = 100`
пропускались целиком, и на реальных данных это стоило двух настоящих
near-duplicate пар: семь пропущенных блоков охватывали 1668 записей, из
которых 1212 не сравнивались вообще ни с чем. Все пропущенные блоки
оказались префиксными и собрались вокруг шаблонных начал отзывов вроде
«фильм очень понравился. » — то есть ровно там, где повторы наиболее
вероятны.

В аудите полнота фиксируется полями `near_blocks_skipped_large` (всегда 0),
`near_largest_block_size`, `near_block_pairs_evaluated` и
`near_candidates_truncated`.

### Кандидаты без решения

Кандидат без ручного решения не удаляется. Раньше это происходило молча;
теперь их число попадает в аудит как `candidates_without_decision`,
список пишется в `reports/data_prep/undecided_candidates.csv`, а подготовка
печатает предупреждение. Локальная проверка считает непросмотренного
кандидата ошибкой: Issue требует, чтобы у каждой близкой пары было решение,
принятое вручную.

### Транзитивность

Подтверждённые пары объединяются в компоненты связности. Если человек
подтвердил A≈B и B≈C, вся компонента считается одной группой, хотя пара A–C
напрямую не подтверждалась. Число таких косвенных пар фиксируется в аудите
как `near_indirect_pairs_in_components`; при ненулевом значении компоненты
нужно просматривать вручную.

### Устаревшие решения

Если решение ссылается на `pair_id`, которого нет среди текущих кандидатов,
подготовка завершается ошибкой со списком всех таких `pair_id`. Это
происходит, когда изменилась конфигурация поиска или когда одна из сторон
пары была удалена раньше точной дедупликацией. Переносить старые решения без
повторного просмотра нельзя.

## Подвыборка train

По умолчанию полные подготовленные данные используются целиком:

```json
"subsample": {
  "enabled": false,
  "size": 0,
  "seed": 42
}
```

Если позже вычислительных ресурсов не хватит, команда сначала фиксирует размер, например:

```json
"subsample": {
  "enabled": true,
  "size": 30000,
  "seed": 42
}
```

После этого обе модели должны использовать один и тот же
`reports/data_prep/train_subsample_ids.csv`. Validation и test не сокращаются
и не балансируются.

## Тесты

```bash
pytest -q tests/test_prepare_data.py
```

Покрываются: отбор языка; class mapping и его неизменность; сохранность
исходного `review_text`; NFC и невидимые символы; пустой и пробельный текст;
пропуски, типы и отсутствующие колонки; недопустимые метки и языки; приоритет
exact-дедупликации во всех трёх направлениях; неизменность test; конфликты
меток внутри split и между split'ами; запрет автоматического удаления
near-duplicates; сохранение обеих строк при `not_duplicate`; выбор
представителя по наименьшему `source_row`; компоненты связности и косвенные
пары; детерминизм поиска кандидатов; валидация конфигурации; файл решений,
включая BOM, дубли и устаревшие `pair_id`; воспроизводимость подвыборки.

Два интеграционных теста создают настоящие Parquet-файлы, прогоняют конвейер
и читают результат обратно. Они помечены `skipif` по наличию `pyarrow`.

## Локальная проверка

```bash
python tools/analyze_blocking_local.py
python tools/verify_t03_local.py
```

Порядок важен: `verify_t03_local.py` требует свежий отчёт независимой
перепроверки, поэтому анализатор запускается первым.

`analyze_blocking_local.py` заново, своим кодом, строит блоки, исчерпывающе
сравнивает все пары внутри каждого блока и сличает результат с набором
кандидатов конвейера. Совпадение наборов доказывает, что поиск полон в
пределах выбранной схемы блокирования.

`verify_t03_local.py` ничего не изменяет: он независимо перепроверяет SHA-256, схему,
пропуски, языки, распределение классов, точные повторы, конфликты меток и
пересечения `movie_id`, запускает конвейер дважды, сравнивает отчёты
побайтово, читает `data/processed/*.parquet`, сверяет их со `split_ids.csv`,
проверяет отсутствие служебных колонок, сохранность `review_text` и
отсутствие cross-split утечек, соблюдение каждого ручного решения, отсутствие
непросмотренных кандидатов и совпадение с независимой перепроверкой поиска. Итог сохраняется в
`reports/data_prep/verification_local.json`.

## Зависимости

Для полного запуска на Parquet нужны как минимум:

```text
pandas
pyarrow
pytest  # только для тестов
```

Общий `requirements.txt` в рамках T03 не создаётся: фиксация зависимостей
относится к задаче каркаса проекта.

## Что остаётся сделать на реальных данных

Чтобы Issue можно было закрыть по всем критериям приёмки, нужно выполнить
`python tools/verify_t03_local.py` в среде с `pandas + pyarrow`, затем:

1. проверить, что все проверки скрипта прошли;
2. просмотреть `reports/data_prep/label_conflicts.csv`, если он непустой;
3. просмотреть кандидатов, для которых `labels_conflict` истинно;
4. зафиксировать решения в `configs/near_duplicate_decisions.csv`;
5. повторить подготовку;
6. приложить `reports/data_prep/audit_report.md` к Issue/PR.

Фактически измеренные величины на текущих исходных файлах: русскоязычные
размеры 77 022 / 10 403 / 9 324, семь точных повторов внутри train, ноль
конфликтов меток. Эти числа конвейер перепроверяет сам при каждом запуске и
не полагается на них.
