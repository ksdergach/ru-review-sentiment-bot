# T14 — влияние Whisper на классификацию тональности

Задача: [#17](https://github.com/ksdergach/ru-review-sentiment-bot/issues/17).
Блокирующая зависимость: T12 ([#15](https://github.com/ksdergach/ru-review-sentiment-bot/issues/15)) —
утверждение моделей и протокола финальной оценки. Набор: T11
([#13](https://github.com/ksdergach/ru-review-sentiment-bot/issues/13), [README_T11.md](README_T11.md)).

**Текущее состояние: подготовительная разработка (этап А).** Инструмент оценки,
метрики и проверки предусловий реализованы и проверены на искусственных данных.
Финальные 36 записей T11 не открывались, Whisper и классификатор на них не
запускались, реальных результатов нет. Финальный запуск отказывает, пока нет
утверждённой фиксации T12 (см. «Зависимость от T12»).

## Что оценивается

Для каждой из 36 записей один и тот же классификатор получает два входа:

1. **Эталон:** ручная транскрипция T11 → классификатор → тональность.
2. **ASR:** аудио → Whisper → тот же классификатор → тональность.

Обе классификации идут через `predict_batch` общего интерфейса `src.classifier`
с одним объектом модели и одинаковым `max_text_length` из фиксации, по одному
тексту за вызов. Распознавание — `src.speech.SpeechRecognizer` с параметрами из
фиксации, без скачивания модели. Отдельной классификации или предобработки T14 не
вводит, код бота не менялся.

Классы и порядок: `negative = 0`, `neutral = 1`, `positive = 2`.

## Метрики

**Классификация** (оба режима, все записи):

- macro-F1 строго по трём классам; класс без предсказаний остаётся в среднем;
- precision, recall, F1, support каждого класса — существующая
  `validation_metrics` из `src/train_baseline.py`;
- верно / неверный класс / нет предсказания;
- матрица 3×4: строки — истинный класс, столбцы — три класса и `error`;
- `ΔF1 = F1_ASR − F1_reference`.

**Распознавание** — корпусный WER:

```text
WER = (ΣS + ΣD + ΣI) / ΣN
```

S, D, I — замены, удаления, вставки минимального выравнивания слов (Левенштейн),
N — слова эталона после нормализации; суммы берутся по всем учитываемым записям,
а не усредняются WER отдельных записей. Среди равноценных выравниваний выбирается
замена, затем удаление, затем вставка; сумма S + D + I от этого не зависит.

## Пустые ответы и сбои

| Ситуация | Статусы | Предсказание | WER |
|---|---|---|---|
| успех | `asr_status=ok`, `asr_classification_status=ok` | класс | S/D/I выравнивания |
| пустая транскрипция | `asr_status=empty`, `not_run` | `error` | D = N |
| технический сбой Whisper | `asr_status=error`, `asr_error_code`, `not_run` | `error` | по правилу фиксации T12 |
| ошибка классификатора на эталоне | `reference_status=classifier_error` | `error` в режиме эталона | не зависит |
| ошибка классификатора на тексте Whisper | `asr_status=ok`, `asr_classification_status=classifier_error` | `error` в режиме ASR | S/D/I выравнивания |

- Ни одна запись не исключается: метрики считаются по всем 36, состав сверяется
  с ожидаемыми ID.
- `error` — служебное «нет предсказания», не четвёртый класс: оно снижает recall
  истинного класса и не входит в среднее F1. В `neutral` или другой класс оно
  не превращается.
- Ошибки Whisper и классификатора хранятся в разных полях и считаются отдельно.
- Ошибкой классификатора считаются исключения его контракта (`ClassifierError`,
  `InvalidTextError`, например текст длиннее `max_text_length`). Иные исключения
  означают дефект и прерывают оценку без записи результатов.
- Технический сбой Whisper: `all_deletions` (D = N) или `excluded` (запись вне
  числителя и знаменателя WER). Какое правило применяется, задаёт фиксация T12;
  значения по умолчанию нет. Число сбоев выводится отдельно в обоих случаях.

## Время

По каждой записи: `asr_seconds` (`SpeechResult.elapsed_seconds`: декодирование и
распознавание), `reference_classifier_seconds`, `asr_classifier_seconds`,
`total_seconds` (распознавание и классификация результата Whisper подряд, как в боте).
Загрузка классификатора и Whisper и прогрев классификатора тремя фиксированными
текстами не из T11 измеряются до основного прохода, отдельно. Прогрев Whisper —
по необязательному `--warmup-audio` (файл не из T11, проверяется по SHA-256).
В сводке — сумма, среднее и медиана. Сетевая задержка Telegram не измеряется.

## Зависимость от T12

Формат фиксации T12 не утверждён, поэтому T14 не задаёт её окончательную схему.
Из фиксации нужны (`EvaluationProtocol`):

- отметка об утверждении;
- классификатор: `classifier_backend`, `classifier_report_path` и его SHA-256,
  при необходимости `classifier_model_path`, общий `max_text_length`;
- Whisper: путь к конфигу и точные значения его параметров (модель, revision, устройство и т. д.);
- T11: SHA-256 `reports/voice_test/composition.json` и `content_sha256`;
- ID утверждённых правил нормализации WER (регистр, пунктуация, числа, токенизация);
- правило учёта технических сбоев Whisper в WER.

Пока T12 не утверждена:

- `PROTOCOL_ADAPTERS` и `APPROVED_NORMALIZATIONS` пусты;
- `python -m src.evaluate_voice --freeze <путь>` завершается с кодом 2: без
  файла — `T12 freeze not found`, с файлом любой схемы — `No approved T12 protocol adapter`;
- отказ происходит до валидатора T11, загрузки моделей и чтения приватных данных.

`provisional_words` (нижний регистр, ё → е, последовательности `\w+`, как `words`
валидатора T11) — черновые правила только для тестов. Это не утверждённая
нормализация, финальный запуск её не принимает. Числительные и дефисы в ней не
обрабатываются. WER принимает любую функцию «текст → слова», поэтому утверждённые
правила подключаются без изменения алгоритма.

## Порядок финального запуска (этап Б)

1. Добавить адаптер утверждённой схемы T12 в `PROTOCOL_ADAPTERS` и функцию
   утверждённой нормализации в `APPROVED_NORMALIZATIONS`. Правила берутся из фиксации,
   без подбора по финальным данным. Добавить тесты адаптера и нормализации.
2. Положить файлы T11 по путям из [README_T11.md](README_T11.md) и проверить
   `python tools/validate_voice_test.py` (без `--write`), установить модели из фиксации.
3. Проверить предусловия без загрузки моделей:

   ```bash
   python -m src.evaluate_voice --freeze <фиксация T12> --check
   ```

4. Финальный запуск:

   ```bash
   python -m src.evaluate_voice --freeze <фиксация T12> [--warmup-audio <файл не из T11>]
   ```

   Порядок внутри: фиксация → публичные входы → валидатор T11 → 36 записей →
   загрузка и прогрев → оба режима → повторная проверка T11 → запись результатов.
   Код 2 — отказ по предусловиям или данным, 1 — ошибка выполнения, 0 — успех.
5. Сверить `metrics.json` с `records.json`, закоммитить только `reports/voice_eval/`.
   Модели, параметры и набор после просмотра результатов не меняются.

## Ограничения исследования

Будут указаны и в итоговом отчёте:

- малый размер голосового теста — 36 записей, по 12 на класс;
- предметная область — отзывы о фильмах;
- четыре диктора;
- часть записей с умеренным бытовым шумом;
- интонация и эмоциональные акустические признаки не анализируются;
- результаты не распространяются автоматически на любые сообщения Telegram;
- время локальное, без сетевой задержки Telegram API.

## Проверка

```bash
python -m pytest -q tests/test_evaluate_voice.py
```

Тесты используют искусственные тексты, файлы и подменные Whisper и классификатор.
Ожидаемые значения посчитаны вручную. Проверяются:

- S/D/I и корпусный WER, его отличие от среднего по записям;
- пустая транскрипция, оба правила учёта сбоев;
- macro-F1 по трём классам, в том числе при классе без предсказаний и при `error`;
- пять видов исхода и полнота записей;
- совпадение и порядок ID, отказ при неполных или противоречивых данных;
- отказ без утверждённой T12 до доступа к данным и моделям;
- отсутствие приватных текстов в публичных отчётах;
- неизменность входов.
